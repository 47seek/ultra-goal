# Ultra-Goal

[English](./README.md) | [中文](./README_cn.md)

> 为 Codex、Claude Code 等 Agent 设计的任务协作 Skill，用于完成持续数小时乃至数天的复杂任务：先调研、出计划，经使用者确认后分阶段自主推进，只在必要时暂停。

## 安装

直接让 Agent 安装：

> Install `ultra-goal` from <https://github.com/Azure99/ultra-goal>.

也可以通过 `skills` CLI 安装：

```bash
npx skills add Azure99/ultra-goal --skill ultra-goal
```

## 工作方式

主 Agent 负责推进全程，调研、review 等工作可委派给子 Agent。调研期查明现状、验证关键方案，形成总体计划。计划就绪后暂停，请使用者确认，同时询问可拆分的阶段是否并行，以及 push、部署等需单独授权的操作是否一并授权。确认后进入实施期，连续推进，不逐阶段请示：每个阶段依次完成阶段计划、实施并验证、独立 review 和本地提交。全部完成后进行整合 review 与整体验证，再向使用者汇报。

只在以下时机暂停：

* 调研期提出问题批次；
* 计划就绪；
* 实施中出现影响后续工作、需要使用者处理的事项（待决问题、授权需求、阻塞），此时先完成不依赖它们的工作，再集中提出；
* 全部完成。

每个任务一个记录目录 `ultragoal/YYYY-MM-DD-task-name/`：顶层的 `README.md`、`decisions.md`、`plan.md` 是入口与权威记录，详细材料放在子目录。该目录不纳入产品提交，用于中断后接续和检索历史任务。

小而明确、且使用者要求直接完成的任务走简化流程：写简要计划后直接实施并验证，完成后做一次独立 review，然后提交并汇报。

## 设计理念

Spec-Driven Development 已是 AI 辅助开发的事实标准，但仍有三个痛点：关键实现决策仍需使用者逐一裁定；超长程任务无法在动手前写尽 spec；中途发现计划不可行时，回退与重规划的成本很高。

Ultra-Goal 的应对方式：

* **先调研，问题集中提出。** 能查证的事实自行查证，常规的专业判断自行决定并记录；只问使用者独有的信息、会实质改变结果的取舍和授权。决策类问题附候选方案与推荐方案，使用者可以回复「其余按推荐」，不必逐一裁定。
* **总体计划定方向，细节留给各阶段。** 复杂任务的细节难以在初期写尽，总体计划定下交付内容、验收标准和阶段划分，阶段计划到各阶段开始时依实际状态编写；实施中与计划不符、且不影响已确认范围时，自行调整后续阶段并记录原因，有影响时才交由使用者裁决。
* **确认后自主推进，只在必要时暂停。** 使用者确认进入实施，即授权修改与按阶段本地提交；技术障碍先自行排查、尝试替代方案，只有使用者才能处理的事项才会暂停。
* **流程繁简与任务相称。** 时间和 token 都是成本，文档、review 和测试的多寡不代表质量；做到什么程度由使用者要求、项目约定和实际使用场景决定，既不擅自复杂化，也不擅自简化。
* **目标保持适度抽象。** 使用者只需给出清晰的目标与验收标准，无需预先设计完整的实施细节。

## 适用场景

启动一次流程会在调研、review 和记录上投入 token，「添加一个按钮」「修复一个 typo」这类局部改动并不划算。Ultra-Goal 适合：

* 持续数小时乃至数天的复杂任务：大型重构、跨技术栈迁移、从零搭建完整模块，也包括调研报告、技术方案等非代码交付；
* 使用者无法持续盯着屏幕：问题集中回答，计划确认后自主推进，只在必要时暂停；
* 并行推进多个项目，希望降低持续决策与监督成本。

## 模型选择

主 Agent 应使用当前能力最强的模型，例如 `Claude Code + Opus 5.5`、`Codex + GPT-6 Astra`；如果模型能力不足，整个流程很容易失控。子 Agent 的模型由平台默认决定；对成本敏感时，可以在请求中显式指定更小的模型。

## 使用建议

1. **目标应清晰，但不含实施细节。** 合适的目标如：「把这个 Express 项目迁移到 Fastify，保持现有 API 行为不变，所有现有的集成测试和 E2E 测试必须继续通过。」目标过于模糊（「改一下项目」）时，调研期会先单独询问一两个决定方向的问题，其余问题再集中提出；写成具体实施步骤（「第一步先改 `server.ts`……」）则会挤占探索与规划空间，反而可能降低质量。
2. **尽量提供端到端的验收方法。** 仅依赖单元测试通常不够，Agent 完全可能让测试通过但功能实际不可用。Web 应用可让 Agent 用 `playwright-cli` 驱动真实浏览器验证关键路径；CLI 工具执行真实命令，校验 stdout、退出码和生成文件；服务端 API 启动真实服务进程，用 `curl` 验证关键 endpoint。
3. **必须显式调用，改代码的任务需在 git 仓库内执行。** 本 Skill 不会被自动触发，这是有意为之：运行成本较高，应由使用者主动发起。实施期按阶段本地提交，因此需要 git 仓库；不在 git 仓库时，会在第一批问题里询问是否初始化，不打断调研。非代码任务以检查点代替提交。

## 从 v1.x 升级

* **`prepare-ultra-goal` 和 `ultra-goal-heavy` 已移除。** 目标澄清并入 `ultra-goal` 的调研期；多路独立规划与交叉评审不再单独提供，需要更多 review 时可以在请求中说明。
* **改为集中提问、按需暂停。** v1.x 进入执行后全程不询问使用者；新版在调研期集中提问，计划就绪后等待确认，实施中遇到需要使用者处理的事项也会暂停。
* **记录目录改为 `ultragoal/YYYY-MM-DD-task-name/`。** 结构与 v1.x 的 `ultragoal/<goal-name>/` 不同。

卸载旧 Skill（全局安装的加 `-g`）：

```bash
npx skills remove prepare-ultra-goal ultra-goal-heavy
```
